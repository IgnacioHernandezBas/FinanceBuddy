==================================================
PROJECT OVERVIEW
==================================================

Goal:
Build FinanceBuddy, a production-oriented financial education assistant powered by a RAG (Retrieval-Augmented Generation) system.

The assistant should help users understand topics such as:
- taxes
- mortgages
- bills
- personal finance concepts

The system must be:
- full-stack
- production-oriented
- modular and scalable
- suitable for portfolio and technical interviews
- designed so it can evolve from MVP to a more advanced real-world system

Core Product Idea:
FinanceBuddy is not just a chatbot. It is a grounded financial education assistant. The language model should not answer from unsupported memory alone. Instead, it should answer using retrieved evidence from trusted sources and clearly expose those sources to the user.

Key Requirements:
- Responses must be grounded in reliable sources
- Always show the sources used
- Minimize hallucinations
- Support different explanation levels, such as "basic" vs "technical"
- Be able to admit uncertainty when the retrieved evidence is incomplete
- Refuse or avoid unsupported answers when evidence is insufficient
- Support future expansion to document analysis (for example PDFs such as invoices, contracts, or mortgage documents)

==================================================
ARCHITECTURAL PRINCIPLES
==================================================

Main Architectural Principle:
- The model is NOT the source of truth - retrieved documents are

This means the system must be designed to support:
1. grounded answers
2. partial answers with uncertainty
3. safe refusal when evidence is insufficient

Additional Design Principles:
- Retrieval and generation must be decoupled
- Every answer must be traceable to source chunks
- The database is a core part of the RAG system, not just storage
- The system should persist enough information to support future observability, source tracing, evaluation, and feedback loops
- Build the data foundation early so ingestion, retrieval, and grounded generation can be implemented cleanly later
- If agent orchestration is introduced, it must preserve explicit workflow control and source provenance

==================================================
HIGH-LEVEL ARCHITECTURE
==================================================

The system is organized into four main layers:

1. Frontend
   - Chat interface
   - Explanation level selector
   - Display answers and supporting sources
   - Later: feedback and source inspection UX

2. Backend API
   - REST endpoints
   - Request validation
   - Application orchestration
   - Later: retrieval, generation, and agent workflow coordination

3. Data Layer
   - PostgreSQL as the relational source of persistence
   - pgvector for vector similarity search
   - Stores trusted sources, chunks, conversations, retrieval traces, feedback, and later agent execution traces

4. Model / RAG Layer
   - Embeddings for retrieval
   - Query-time retrieval over trusted chunks
   - Prompt construction using retrieved context
   - LLM generates grounded answers only after retrieval
   - Later: LangGraph-based orchestration for controlled branching and optional web lookup
